# 核心方法论
<!-- maintenance-purpose:start -->
维护的目的是减少用户重复解释、agent 遗忘和返工，把有价值的信息整理成以后能找到、能使用的 memory，并修正失效内容。允许本轮不新增任何 memory；更新、合并、删除和确认无需更新都是合理结果。
<!-- maintenance-purpose:end -->

<!-- maintenance-criteria:start -->
* 如何限制agent：有些要求只能提高遵守概率，无法硬性保证；但是在增加每一个rule的时候，就必须想好一个rule的生效level：
  * level0必然生效：通过在repo中增加一个hook来确定性永久解决。比如，我们有一个场景，不想让agent调用某个xxx程序。我们可以做一个codex hook，拦截一切xxx的调用。
  * level1有成本地几乎必然生效：
    * 例如，将rule通过hook，硬性加载到每一次对话中的上下文中，或者比如固定每1000token插入一次，或者检查到特定关键词，或者每次compact后固定trigger一个文件的读取，就插入一次固定prompt等等，通过增加token成本来讲遵守概率提高，但是也无法做到100%遵守。
    * 例如，派遣单独的agent进行审阅。
  * level2通过agent markdown等memory（泛指一切agent.md，rule.md等）这种不可靠介质中，增加遵守概率；这种的最容易产生无效rule，因此强烈建议和level1配合使用。


* 如何给予agent memory：codex等工具一般都有自己的memory系统。我们也可以有自己per repo的memory系统。如何保证我们这些文档
  * （实时性）得到统一的及时的更新，有明确的更新责任人和更新时机。
  * （真被用）有明确的功能定位，有明确的调用时机，保证他们真的被使用，且好用。
  * （信噪比）文档的效率要高。历史垃圾文档得到清理，文档的size容量可控，没有重复文档，文档和代码等有明确的边界，而不是复读代码。谁来删减文档，什么时机进行删减文档。

是我们memory系统的重点。刚才的rule其实是memory系统的一个类别。level1和Level2的rule是memory的一部分，而memroy的维护也是一种rule。


因此，我们必然的需要一些level0的rule作为基石，制定一些基本的memory管理规则，来实现rule类memory的闭环自洽，自我约束和自我维护。

然后基于这些rule类memory，去拓展维护其他memory。
<!-- maintenance-criteria:end -->


# 基石rule，对每一个项目都起到开天辟地的作用：
<!-- maintenance-boundaries:start -->
* **level0rule[防止膨胀]**：每份 memory 和每次加载的 memory 总量有容量预算；由 hook 检查，超限则报警并打回 agent 精简，允许暂时超限。检查和报警由程序保证，精简质量需要 agent 判断；加载器不承担容量拦截，继续加载完整正文。
* **level0rule[无流浪文档]**：由 hook 或后台脚本在约定范围内检测未登记或脱离文档树的文档，并提醒 agent 处理，让文档体系保持树状结构。程序保证检测与提醒，后续的反省和归位由 agent 完成，属于 level1。
  * 提醒 agent 判断：临时产物是否需要保留在这里；重复内容能否合并进已有文档；独立长期 memory 是否值得纳入体系。
  * 确有独立长期价值时，说明用途、归属和理由，按约定审批后登记。未登记不等于垃圾，不能为了消除提醒机械登记或删除。
  * 程序不拦截文件操作，不自动删除或登记；采用“发现 → 反省 → 归位”的处理方式。
* 维护时更新唯一正文，按登记关系查找现有位置；区分方法论、例子和已实现机制，例子不自动构成任务。新增 rule 要核实实际触发方式和覆盖边界，不能把写进文档当成程序已实现。
<!-- maintenance-boundaries:end -->
* **level1rule[恢复记忆]**：在 compact 后，通过 hook 加载信息到第一次对话上下文中；材料从当前有效 memory 中生成，包含纲领信息、memory 地图、遗忘提醒。让模型知道自己刚经历 compact、可能丢失了记忆，需要按地图主动回顾相关 memory；无需事无巨细地注入全部文档。启动和 resume 同样提供恢复入口，但只按实际事件说明，不误称刚发生 compact。
<!-- maintenance-procedure:start -->
* **level1rule[维护内容]**：基于/loop等机制，强制定期触发 agent 更新 memory，同时清理被替代、重复和失效的信息。这个loop应该注入类似的提示词
  * 请反思之前的经验教训，进度状态，是否要落成memory；同时，也允许本轮不产生任何 memory；允许更新、合并或删除现有内容
  * 对于需要落成memory的内容，先列举出来；区分经验教训/进度/笔记/rule。
  * 对于列举出来的，逐个判断应该落成level几的memory。并反思是否实践闭环
    * 例如，level0的一些确定性坑，举个例子：发现机器不能使用xxx命令，则建议使用hook做确定性拦截。
    * 例如，可以约定一个level1的todolist，对每一个任务，在todolist中设置一个确定性的状态机，用hook拦截任何非法状态，在某个任务的状态发生翻转的时候，确定性hook trigger一些时间，例如跑回归，做头脑风暴，更新文档等。
    * 例如，可以约定一个level1的/loop，定期做一些有必要，但是不好hook，或者可以低频维护的动作。例如，定期pull上游并merge。
    * 例如，codemap，性能调优经验等，可以落成level2的memory，但是要在level0/level1中，确定性的有指向他们的链接提示词，让他们不被丢。同时通过level0rule[无流浪文档]检测并提醒agent处理归属问题。
  * 先核对本阶段的用户决定、任务进展、失败经验和已改变的事实，再列出候选；优先更新、合并或删除已有内容。找不到事实依据时明确说明信息缺口，不编造经验、不把旧计划当新授权。
  * 完成后检查正文与登记、容量及实际机制是否一致，说明更新位置、无需更新的原因或尚未落实的环节。发出维护提醒不等于维护已经完成。
  * 定期维护是整理频率，不是防遗忘保证。重要信息应在仍可确认时及时保存到获准的现有位置；从未保存且已遗忘的事实无法靠再次注入方法论恢复。
<!-- maintenance-procedure:end -->
* **level0rule[冷文档检测]（暂缓，未实现）**: 这是一个候选兜底策略；由hook或后台脚本定期检测，是否存在
  * 使用RRPV等策略，管理识别那些被使用频率相对特别低的文档。但是read其实不好做，因为grep不经过你。
  * 如果存在，则报警给agent处理。

# 文档体系与恢复入口

以纲领为文档树的根，通过 memory 地图组织和查找其他 memory，由 level0rule 检查约定范围内的结构与容量。恢复材料由 hook 从当前有效 memory 动态生成，包含纲领信息、memory 地图和与实际事件对应的遗忘提醒；其他 memory 由 agent 按需回顾。

# 具体实践

* [memory.json](./memory.json)：基础设施，登记文档树、检测范围和容量预算。
* [scripts/check_memory.py](./scripts/check_memory.py)：`level0rule[无流浪文档]` 与 `level0rule[防止膨胀]` 的检测器；发现未登记文档时附带反省和归位要求，不拦截文件操作。同一批未登记文档在工具回调中去重，恢复会话和定期维护时复查。覆盖范围见 [AGENTS.md](./AGENTS.md)。
* [scripts/load_memory.py](./scripts/load_memory.py)：`level1rule[恢复记忆]` 的加载器，在启动、resume、compact 后注入纲领正文、从 memory.json 生成的文档树地图、与事件对应的遗忘提醒；其他 memory 按需回顾，不整库注入。实际启用状态见 [AGENTS.md](./AGENTS.md)。
* [scripts/maintain_memory.py](./scripts/maintain_memory.py)：`level1rule[维护内容]`，复用工具结束 hook，每 50 次工具调用注入维护目的、完整判断标准与操作边界、完整维护流程，以及当前事实回查入口；正文从本文标记区段提取，频率在 memory.json 中调整，允许无需更新。
