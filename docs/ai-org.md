# 照着起一个同样的 AI 组织

这篇是操作手册，配套的机制说明在 `canvas-protocol.md`（画布交流协议）。协议讲的是"消息怎么走"，这篇讲的是"人怎么摆"。

先说一句要紧的：**协议管不着组织。** 谁是主管、谁负责哪块、谁能再招人，是你自己定的，协议只保证消息能可靠地送到、完成能被可靠地通知。所以别指望套一份模板就完事——下面给的是我们跑通的形状，你可以改。

## 一、先分清三层

| 层 | 说的是什么 | 会不会变 |
|---|---|---|
| 机制 | 画布允许什么、拒绝什么 | 由 nodeterm 决定，你别改 |
| 约定 | 为了可靠，你该怎么用 | 要写下来，团队都读 |
| 组织 | 谁干什么、谁管哪块 | 你自己定，随时改 |

混在一起的代价是：机制一变，你以为组织也变了；组织一改，你以为机制变了，于是绕路。分开写，分开放。

## 二、岗位怎么设

**一个主管，加若干个专职席位。** 别搞更多层，也别一次开一堆人。

一个席位是四样东西绑在一起：

1. 一个长期活着的 agent 节点（会话别丢，能重启接回来）；
2. 一份它自己的作业文档（它改代码、打包、排错的经验都写在这份里）；
3. 一条明确的路径授权（它只能动哪些目录）；
4. 一句话说得清的职责（"管 LLM 订阅与模型配置"这种）。

**为什么席位要少：** 每多一个席位，你就多一个要盯的回合、多一份要维护的文档、多一处会静默失败的地方。我们的经验是三个以内够用，不够再加。

**主管不包办。** 主管的活是拆工单、派活、验收、收口；具体动手交给席位。主管自己去写代码，是把自己降级成了一个席位，同时没人再看全局。

## 三、工单的标准形状

派活时按这五项写，缺一项对方就会猜，猜就会错：

1. **目标**：一句话说清要什么。
2. **允许动的路径**：只动哪些目录和文件。
3. **完成长什么样**：可验证的判据——哪个测试要过、产物落在哪个路径、输出什么。
4. **禁区**：不许碰的东西，逐条列。
5. **交回格式**：做完交给谁、以什么形式。

长文档用「路径 + 章节」引用，不要把全文贴进工单。工单是单行投递，长文会挤压，甚至触发文件投递那条路（见协议的反例 1）。

**派单之后必须拿回执。** 回复说"已排队"就是没送到。这条不是洁癖：我们真的丢过工单，发送方拿到一句"已排队"，然后一天过去了，对方什么都不知道。

## 四、完成与验收

- **完成信号只有一个**：对方自己跑 `report-outcome`。成功和失败都会推给开它的节点。不要去轮询列表。
- **验收看产物，不看对方的话。** 它说"测试全绿"是它说的；你要么自己跑一遍，要么至少核对产物指纹（文件在哪、什么时候改的、里面有没有这次改动的标记）。
- **失败也是一等信息。** 对方报 `failed` 要当回事，把原因记进台账；别安慰自己说"它可能只是慢"。

## 五、主管自己的纪律

这几条是我们踩过坑之后写下来的，照着做能省很多事：

1. **先入账，再动手。** 每件活先落到台账（一个 CSV 就够：编号、标题、状态、备注），做完改状态。没有台账，一周之后你自己都不知道哪些是活的。
2. **不轮询。** 有人问"它做完了吗"，答案应该是通知，不是你去查。查一次可以，反复查说明机制没搭好。
3. **派单要有回执，拿不到就说"未确认"。** 沉默不是成功。
4. **改了行为，回头扫一遍描述这个行为的旧文字。** 留着一句"以前是这样"，下一个人就按旧行为办事。
5. **删文档之前扫全仓引用**，把指针改到新家。
6. **别留备份垃圾。** `.old`、`.bak`、"副本"这种目录，用完当场删。产物只有一份，就是 canonical 那份。
7. **配额和上下文都要看。** agent 的回合有成本，会话的上下文有上限；快满了就换一个新的席位，把结论先落进文档再换人。

## 六、文档怎么长

**一个席位一份作业文档**，加上主管的台账和一份总纲。够了。

- 研究类的原始产出（调研、扫描结果、对比表）**不要留在仓库里**——把结论写进一份文档，原件删掉。别把过程当成果攒着。
- 一个目录的常驻文档控制在四份以内。新开一份之前，先问"能不能并进已有的那份"。
- 一次性工单（派完就完的活）交付后删掉，记录以台账为准。

这套规矩看起来啰嗦，但它挡的是最常见的死法：**文档越攒越多，没人知道哪份是对的，最后大家都不读。**

## 七、开局的照抄清单

第一天这样做：

1. 开一个节点当主管，给它一份总纲（目标、约束、台账在哪）。
2. 用 `open-agent --agent <cli> --prompt '<它的第一份工单>'` 开第一个席位——**首单随启动命令交出去**，别开个空节点等它上线。
3. 席位第一份工单就写三样：职责一句话、允许动的路径、第一件活。
4. 让它跑完，`report-outcome`，你看通知，去核对产物。
5. 通了之后再把第二件活派下去；不通就查 `list` 里那个节点的信任列和状态，别猜。

第五步是关键。**先跑通一个席位，再谈编队。** 一个席位都跑不通的时候加人，只会把失败复制几份。
