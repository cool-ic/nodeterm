# 画布交流协议（nodeterm）

版本：1.1（2026-10-08）· 唯一权威：`~/.nodeterm/canvas-protocol.md`（机器级，不属于任何项目仓库）

> 1.1 相对 1.0 改了什么：1.0 写的是 T198 之前的世界。这一版按 T190（唤醒）、T191/T204（确认框）、T198（重启后再证明）、T201（信任可见）、T205（队列不静默过期）重写了第 1、2、5、6 节，并订正第 7 节的反例。

**适用范围**：nodeterm 画布上的任意 agent 会话，无论哪种 CLI（Claude Code / Codex / Gemini / Copilot / Grok…）、哪个项目、什么组织架构。本协议只写**机制事实**与**为保证可靠而生的约定**；「谁指挥谁、谁向谁汇报」是各项目自己宪章的事，本文不涉及。

一句话：**画布是总线，节点是工位，消息是唯一的说话方式。**

先分清三层，别混：

| 层 | 内容 | 在哪 |
|---|---|---|
| 机制 | nodeterm 允许什么、拒绝什么 | 本文第 1–6 节的事实陈述 |
| 约定 | 为了可靠，你该怎么做 | 各节「约定」条目 |
| 组织 | 汇报关系、路径授权、扩编口径 | 各项目的宪章（不在本文） |

## 1. 握手：对方存在吗，什么时候能说话

**机制事实**

- Agent 状态只在**回合边界**上报：一轮回答开始（WORKING）与结束（done）。没有运行中的回合 = 没有事件。
- 节点首次启动后、第一次回合结束前，它对消息系统是**盲的**（UNCONFIRMED）。App 重启后接回来的节点也是这个状态，直到它跑完一个回合。
- **所有权**：节点是谁开出来的，由「本轮哪个项目真实 spawn 了这个 pane」回答——账本记 `nodeId → 项目的机器本地编号`，不是记调用者的身份。
  - fresh spawn 时，这一行同时落到磁盘（`<userData>/orchestration-state/pane-ownership.json`）。
  - App 重启后节点被 attach 回来时，App 拿认领方的**当前**项目编号去对那一行：对得上就恢复所有权，不必关掉重开。
  - 这条挡的是「git 共享的 `project.json` 自己声称拥有某个终端」——项目编号是本机生成、克隆必异的，伪造的文件对不上。它不挡本机已经在跑的 agent：那种 agent 本来就能直接 `tmux -L node-terminal send-keys -t nt-<nodeId>` 往任意 pane 打字，比这更省事。
- **`list` 会把信任状态打给你看**：每个 agent 节点行尾标「信任：已证明 / 未证明（原因）」，原因是可读的一句话（没有持久行、会话已亡、entry id 不匹配、待再证明、宿主没接线）。纯终端节点不参与消息，不列。读不到账本时整列省略，不猜。
- `link` 建立两节点间的读取链路（默认双向，可单向），建好后 `get-linked-context` 可按需读对方的对话/摘要/终端缓冲。读取是拉取式，不推送，不打断对方。
- 同项目内，任意 agent 节点可给任意 agent 节点发消息——**机制层没有职级闸门**。闸门只有：同项目、目标是 agent 节点、来源检查、**目标 pane 本轮出处可验证**（fresh spawn 过，或按上面的持久行再证明过）、项目消息开关、限流。

**约定**

- 新节点宣告就绪的方式就是**完成第一回合**：开节点时把首单写进启动命令（见第 2 节），回合结束它自然从 UNCONFIRMED 变为 IDLE。不要开一个空节点等它「上线」。
- 接收方首次接触一条派活时：读完工单先确认边界（能做什么、禁区是什么），开工时在任务板/看板认领或回复确认；做不了或边界不清，**退回要说清缺什么**（reply 说明，或 `report-outcome failed --note <原因>`），不要静默挂着。

## 2. 下达：怎么把活交出去

**机制事实**

- 首单随启动命令进：`open-agent --agent <id> --prompt '<首单>'`。**不存在「先开节点、再 send 首单」**——首回合前节点 UNCONFIRMED。
- 收编磁盘上已有会话：`open-agent --agent grok --resume <session-id> --prompt '<首单>'`（收编即派活）。只有 grok 支持 `--resume` 与 `--prompt` 并用，其它 CLI 没验过，会被拒。
- **长 prompt 走文件的坑**：prompt 超过预算时 App 把它落成文件，靠启动命令里的 `"$(cat …)"` 替换送达。若启动命令里**既没有字面量也没有 cat 替换**，首单就被静默丢了——识别特征：会话恢复成功、节点停在输入框、首单从未开始。已修，但旧包仍在野外，收编后核对首单确实开跑。
- `send` / `reply` = 信封通道：带发送者、编号、正文，可排队，进不了斜杠命令。`write` = 键盘通道：模拟人打字，能进斜杠命令、能提交输入框。
- **忙则排队不打断，但排队不再等于会丢**：目标正在回合中时消息进队列，等它空闲下来再送。**目标活着，队列里的消息就不会过期**——agent 一回合常常十几二十分钟，远超旧的 5 分钟上限，所以那条「超时」规则改成了：只有**探针确证会话已死**才过期，且发送方会收到回执（dead-letter），不是静默作废。回执分三态：tmux 亲口答「没这个会话」才说 gone，**问不到就说「无法确认」**，不替对方宣布死亡。`queued ≠ delivered` 仍然成立：字节没进对方 pane 之前都算没送到。
- 限流：同一对节点 10 秒最多 1 条；一个发送者每回合最多发 4 个目标。

**约定：一份工单的标准形状**

1. **目标**：一句话说清要什么。
2. **允许动的路径**：只动哪些目录/文件。
3. **完成长什么样**：可验证的完成判据（测试过、文件在哪、输出什么）。
4. **禁区**：不许碰的路径与动作，逐条列出。
5. **交回格式**：做完交给谁、以什么形式。

长文档用「**路径 + 章节**」引用（读 `X.md` §N），**不把长文贴进工单**。

**约定：下达后**

- 回复是 `queued` 就没送到：等目标空闲、状态变新鲜后再核对是否真送到，别干等。
- 要进对方 CLI 的斜杠命令（`/model`、`/quit`、shell）只能用 `write`；`write` 会打断或插入对方正在做的事，能不用就不用。

## 3. 反馈：怎么知道做完了

**机制事实**

- `report-outcome --outcome succeeded|failed [--note '<一行>']`：节点对**自己任务**的结论。App 代发一封 station notice 给 opener（成功失败都发），不走消息队列、不依赖对方记得发消息。
- `succeeded` 的语义是**验过**：按工单的完成判据核对过，不是「我停了」。`--after-success` 挂着的下游只认 `succeeded`。
- 站点消失还有三类失败通知会推给 opener：回合因错误结束、站点被关闭且未报成功、提问无人回答。
- 投递回执三态：`delivered`（字节已进 pane）/ `queued`（等空闲）/ 拒发（`notPermitted` 系列，带原因）。`queued ≠ 送达`。

**约定**

- `report-outcome --note` 有长度上限（实测约 200 字符），超了会被截断（截断处留省略号）。**长内容写进文件，note 只放路径**——和给工单定的规矩是同一条：正文走文件，口头只报地址。
- **通知是信号，不是账。** 完成通知与死信只用来叫醒 opener；App 侧那些记录文件（例如 `orchestration-state/station-outcomes.json`）**每次重挂会被整体重写**，不能当历史查。要留痕就写进文件或台账。
- **完成信号 = `report-outcome`**。不要轮询 `list`（烧回合、烧 token），不要拿 `send`/`reply` 当完成汇报。
- opener 收到 notice 才算收口。
- 接单：reply 或任务板认领。退回：`failed` + note 说清原因。求助：CLI 有提问机制（节点状态 NEEDS YOU），把问题留给能回答的人。

## 4. 编排：依赖与时序

**机制事实**

- `open-* --after <id[,id]>`：挂起新节点，直到列出的 station 完成一回合才启动。挂的是**新节点**，不会叫醒已在跑的人。
- `--after-success <id>`：同上，但还要求对方 `report-outcome succeeded` 且回合结束。
- 给已跑的 station 递新工作（send/reply/write/run）会重置它的「完成」：之前那个 `done` 释放不了任何东西，要等**新工作到达之后开始**的回合结束。
- 链上的站报了错（LAST TURN ERRORED）或被用户打断（LAST TURN INTERRUPTED），不释放依赖——重试或人工 `run`。

**约定**：依赖边用 `--after` 表达，不写轮询循环；「先交新活、再挂下游」，顺序反了下游立刻空跑。

## 5. 恢复：App 重启之后

**机制事实（全部实测过）**

- 节点壳由画布 attach 重建，会话文件在磁盘，记忆不丢。
- **所有权从磁盘恢复**：attach 时 App 用认领方的项目编号去对持久 spawn 行，对得上就自动恢复，`send`/`reply` 照常。所以「重启后谁都发不进去」是 T198 之前的行为，现在只有**对不上**的才拒（克隆的项目、被删掉的行、手工在 tmux 里 resume 出来的 pane——后者从没经过 App 的 spawn 路径，所以没有行可对）。被拒时读拒绝文案，它写着唯一可行的自愈路径（把会话重收编成 fresh spawn）。
- **唤醒**：对「本轮没有任何观察」的 station（attach 还原、或从没报过状态），**记录在案的 opener** 发 `send` 会直接投递——信封进 pane 就是唤醒，回合随之开始，状态变新鲜。**不豁免的三种**：`targetBusy`（已验证在忙，排队不打断）、`idleInferred`（对方可能正停在审批提示上，打字会替它作答）、会话边界/状态过期（CLI 跨了边界，需要人或重启）。
- **非 opener 对未验证 pane 不是排队，是当场拒发**：账本只记 spawn、不记回合，目标跑多少回合都不产生记录。
- station notice 对冷恢复的 opener 也投递，同信任级。T205 之后，只要目标会话活着，排队中的通知就不会因为时限作废。
- 「不再询问」的勾选框**默认不勾、作用域是本次运行**；想让它持久，得自己勾上并选 project 作用域（见第 6 节）。框弹出来的时候，默认不会替你买下任何超出这次的东西。

**约定**：重启后第一件事是跑一次 `list`，看每个节点的信任列——「已证明」的直接派活，「未证明（原因）」的按原因处理（重收编 / 让它跑一回合 / 忽略）。被拒了读拒绝文案。

## 6. 边界

- **预算**：fan-out 每回合 4 目标；配对 10 秒 1 条。超限的回复都带原因，照着办即可。队列时限只对**已死的会话**生效，且过期会通知发送方。
- **破坏性动作的确认**：`write` / `close` / `run` 这类动作在人确认后执行。**默认自动批准**的条件是「每个目标都过得了投递闸的所有权检查」——本轮可验证的 pane，或你就是它的记录在案的 opener；自动批准会留痕（`control-auto-approved`）。写入**自己**的 pane 仍然要人点。`open-project`、`settings` **永远**人工确认，不可豁免。「不再询问」的勾选框默认不勾、作用域仅本次运行；要持久，勾上并显式选 project 作用域。
- **项目消息开关**：每项目一个总开关，关了全部消息动词静默失效（拒绝会说明）。
- **人也是参与者**：人会在 pane 里打字、会点头或拒绝确认框、会写看板评论（评论以信封投给被 @ 的节点）。人打字不算「交接新任务」；判断一个节点是不是真在干活，看它的回合与 `report-outcome`，不看输入框里有没有字。
- **组织与机制分离**：本协议不回答「谁能指挥谁」。把它写进你项目的宪章。

## 7. 反例清单：你会怎么被骗

**反例 1：长 prompt 被静默丢弃。**
收编（`--resume`）时 prompt 超预算被写成文件，启动命令里却没有任何 prompt 参数——会话恢复成功、静静停在输入框、首单从未开始、节点 UNCONFIRMED，随后对它的 send 全进队列。你看到的表象是「对方啥都没做」。**防**：收编后核对首单确实开跑（它该有自己的第一回合）；没跑就补一条 `send` 或重开。

**反例 2：把 `queued` 当成送达。**
`send` 返回 `queued` 只说明「进了队列」，真正送进去要等目标空闲。T205 之后，只要还能确认目标会话活着，它就不会因为超时被丢掉；只有确证会话已死才作废，并给你一条回执——回执会写明是「确证已死」还是「问不到」。但没送到就是没送到。表象：对方一直空闲、你这边毫无动静。**防**：重要的活走 `--after-success` + `report-outcome`，让完成信号自己走过来；长时间没动静就查目标的信任列与状态，别假设。

**反例 3：产物不在约定路径却报完成。**
打包/构建的产物挪进了错误位置（例如目标目录已存在时，`mv` 把新产物套进旧目录里层），canonical 路径上还是旧货，而报告说「已交付」。表象：对方换上了「新包」，行为却是旧的。**防**：交付前自检 **canonical 路径**的产物指纹（修改时间 + 本次改动的标记字符串），不过自检不许报完成。

**反例 4：为不存在的闸门绕路。**
你以为平级之间有「等级闸门」、消息要经第三方转发——机制里没有这条闸。同项目内 `send` 直接可达；绕路只会给中间节点加无意义的回合。先查拒绝原因，再决定要不要绕。

**反例 5：拿「本轮没观察」当「对方在忙」。**
一个 attach 还原、还没跑过回合的节点，面板上看着空、状态写着 UNCONFIRMED，它其实收不到消息。要是你正好是它的 opener，你的 `send` 会唤醒它；不是的话，它当面拒你，不会替你排队等。**防**：看 `list` 的信任列，别拿「看起来闲着」当可投递的证明。

**反例 6：把长内容塞进 note，被截了还以为对方看到了。**
`report-outcome --note` 有长度上限，超出部分被切掉、留一个省略号。你以为把两条结论都报上去了，对方只收到第一条的一半。**防**：长内容写进文件，note 只写路径——这条和「工单按路径给」是同一条规矩的两面。
