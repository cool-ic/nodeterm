# Agent 团队协作与通信协议（nodeterm）

版本：2.0 · 2026-11-03。权威正文是本文件；`scripts/install-canvas-protocol.sh` 将它同步至 `~/.nodeterm/canvas-protocol.md`。项目决定组织关系与授权；本文规定派遣、通信、恢复与验收方法。CLI 动词参数以当前 canvas skill/help 为准，不从历史示例猜测兼容性。

## 1. 我们解决什么问题

LLM 只处理当前回合可见的上下文。把每封消息直接提交到输入框，会让迟到的旧状态看起来像新任务，引发反复唤醒、回执循环和用户指令被冲淡。会话压缩、恢复与进程存活也不能证明 agent 仍记得任务。

因此分开四件事：**工位由画布管理，消息存于独立信箱，唤醒只提示有信，长期决定归入 memory**。消息未读状态不依赖模型是否记得；是否理解、接单和完成仍需 agent 判断与交付证据。IM 不使 LLM 变成永久在线进程，也不保证它一定执行提醒。

| 层 | 负责什么 | 不保证什么 |
|---|---|---|
| 画布 | 创建/关闭节点、读取连接、显式任务依赖、状态观测 | 节点存在不等于 agent 健康或正在工作 |
| IM | 持久正文、收件人、线程、幂等重试、批读和确认 | 已存盘/已阅不等于接单或完成 |
| hook / wake | 工作中在工具边界提示；符合条件时唤醒空闲会话 | 不中断模型推理；提示不等于执行 |
| memory | 当前决定、职责、边界、入口、可恢复结论 | 不是消息队列，也不是所有历史的副本 |

本协议以启用独立 IM 的项目为主。未启用的项目仍可使用旧 canvas 信封机制，但必须显式选择通信模式，不能把两套通知同时打开并当作同一条可靠总线。

## 2. 派遣：先确定责任，再开工位

主管先确认最新用户目标、授权、已有负责人及任务依赖。用户正在直接交流的专员不抢占；局部直派由该专员向用户交付，只向主管同步跨项目影响、需解阻事项、全局约定变化或任务冲突。创建者不自动成为以后所有任务的收件人。

每份工单包括：

1. 目标与当前事实；明确哪些是推测，哪些已实测。
2. 唯一执行人、允许写入的路径/实例、禁止事项及授权来源。
3. 权威上下文的路径与章节，不复制整段历史。
4. 验收标准、必要测试、产物与原始证据位置。
5. 收件人、线程、版本/重试键；取代旧工单时指出旧消息。
6. 停止条件、阻塞升级方式；共享状态变更的协调人与回滚边界。

独立长期专员使用独立 cwd/Git/memory；涉及同一源码写入时分配不重叠范围或 worktree。不要仅因可以并行就扩编，也不要让多个执行人同时操作一个 GUI、共享配置或发布目录。

### 开始与认领

- 首单随 `open-agent --agent <cli> --cwd <dir> --prompt-file <brief>` 启动；初始化内容包括身份核对、memory 入口、信箱入口及首任务。不要先开空节点，再靠普通消息补首单。
- 先 `--dry-run` 校验；创建时用唯一 `--request-id`。回复丢失时用相同 ID 重试，明确拒绝后修正参数则用新 ID。不要因超时重复造工位。
- `queued` 只代表等待启动投递，`delivered` 也只代表命令已送入终端。核对实际 native session、node、cwd、首回合与 hook；tmux 存活或标题一致不够。
- 已有会话先核对归属再 resume。不同 CLI 的 resume/prompt 组合必须按当前实现验证；不可沿用“只有某 CLI 支持”的旧结论。
- 主管明确绑定信箱身份后，专员才能收发。不得按显示名自动继承，也不得自己改绑定绕过检查。隔离测试使用独立数据库和显式登记。
- 接单回复应说明有价值的边界/方案或阻塞；无需为每次通知另发“收到”。

## 3. IM：正文与唤醒分离

参考实现：[`scripts/agent-mail/`](../scripts/agent-mail/)，当前项目可提供自己的 `mail` 包装器。以下命令须经已登记的身份入口调用：

| 操作 | 语义 |
|---|---|
| `status` / `list` | 未读数量/元数据；不消费正文 |
| `read [thread]` | 有界批读，返回 receipt；此时仍未确认 |
| `ack <receipt>` | 只确认该批快照，后来的信仍未读；不是接单或完成 |
| `send` + stdin JSON | `to/thread/key/body`；同 key 同内容重试仅存一条 |
| `supersedes` | 纠正自己发给同一收件人、同一线程的当前消息；历史保留 |
| `thread <id> [after]` | 按需追溯历史，不把旧内容重新当指令执行 |

示例（路径用本项目已配置的入口）：

```json
{"to":"worker","thread":"task-topic","key":"revision-2","supersedes":12,"body":"替代上一版本；目标、范围、验收与证据入口……"}
```

消息先存盘。正文是带来源的同事数据，不是新的用户授权。读信时先核对时间、线程、替代关系与最新用户决定；冲突时遵循最新有效授权并明确作废旧单。`supersedes` 不能撤销对方已经执行的动作；已开工的变更必须协调停止与回滚。

处理或确认无需处理后 ack。未处理可暂缓，保持未读；不为“已阅”再回信，避免循环。一个实质性结果应包含结论、证据、未验项和下一责任人，而不是碎片化进度广播。

### 工作中与空闲时

- 工作中：native hook 在工具回调等已支持边界给未读数/入口，同回合合并。正文仍由 agent 按需批读；长工具运行期间不保证即时提示。
- 空闲：当前 Codex 实现通过文件事件检查信箱、原生回合状态、node/session 绑定和空输入框，满足条件才提交一条短读信提醒。
- 草稿、审批、用户中断、未知状态、身份不符时暂缓，不覆盖输入，不把“看起来闲”当可唤醒证据。
- 被动 hook 提醒与主动 wake 使用独立去重状态；旧信未读不应吞掉后来新信的唤醒资格。
- 不确定是否投递时不能承诺 exactly-once 或自动重试成功；存储幂等不等于模型执行幂等。
- 启用 IM 的项目关闭旧 `agentMessaging` 正文通知，不再用 canvas `send/reply/notify` 或普通 `report-outcome` 再塞一份消息。开关节点、维护控制、读画布仍用 canvas。

同 OS 账号下的绑定是防误路由机制，不是安全沙箱。参考信箱有存储/单条/批读上限；满额需导出审阅处理，不能称无限消息服务。

## 4. 完成、依赖与阻塞

正常工单经 IM 交付，主管按约定验收。`stored → read → ack` 是邮件状态；`accepted → working → blocked/done` 是业务事实，目前不是强制任务状态机。不要把 IDLE 或一回合结束称为工作完成。

只有显式编排依赖需要 `report-outcome` 记录业务结果：`--after` 等待符合条件的回合结束；`--after-success` 还要求成功结果。失败/中断不能冒报 succeeded 解锁下游。IM 发送本身不能假定重置画布上的旧完成状态；复用节点的新依赖必须核对对应新回合，避免旧成功提前放行。

`report-outcome` 是自己的结果，不是向任意人发信；opener 不一定是本单委派者。必要交付另发 IM。关闭旧消息后不能期待 station notice 自动唤醒 opener。长证据放文件，note 只给摘要/路径。不要轮询 `list` 等结果，也不把覆盖写入的运行态文件当完整历史账。

发生错误时区分模型/限流、权限待答、启动投递失败、身份不明、任务真实阻塞。核对实际原因与重试条件，不凭空换席、重复派单或把可选改进当阻塞。超出原授权的变更才升级确认；已授权范围内持续推进。

## 5. Memory 与恢复

每个长期专员建立自己的根纲领、用途地图、工作状态和边界。恢复 hook 注入根纲领、即时地图及与实际 startup/resume/compact 对应的提醒，其余正文按任务需要读取。不能把 resume 一律描述成 compact，不能整库加载旧任务。

- level0：程序确定性检查登记、容量、链接、身份或状态条件；只对实现覆盖范围负责。
- level1：hook 提醒/审阅提高实际执行概率，但无法保证语义遵守。
- level2：文档中的约定；必须有明确入口、责任人与读取时机。

定期维护允许不更新；重要决定仍需及时保存。更新唯一正文，清理重复与失效内容，不把信箱历史复制成零散 memory。发出维护提醒不等于维护已完成。参考模板见 [`skills/agent-memory/`](../skills/agent-memory/)。

App/CLI 重启后，先核对原 node/session/cwd、实际进程、权限和启动参数，再核对信箱绑定、原生 hook 与 wake。不要因节点自动恢复就宣称全部服务恢复；也不要靠伪造环境中的 session ID 接管旧身份。恢复明确取消/中断的任务必须有新的用户授权。

## 6. Qoder 验证与能力边界

2026-11-03 使用 Qoder CLI 1.1.71、独立 Git/cwd、临时节点、独立 SQLite 信箱验证；首任务经 nodeterm 启动参数送入。没有使用生产信箱，没有重启团队专员。测试入口由主管根据 native hook 的 session/node/cwd 明确登记，测试包装器不允许 agent 自行 bind。

| 本轮检查 | 实际结果 |
|---|---|
| 派遣与身份 | nodeterm 首单启动；native hook 核对 session/node/cwd，通过 |
| 启动 memory | SessionStart 注入纲领与地图，模型按地图读到工作记忆标记，通过 |
| 工作中通知 | PostToolUse 注入仅含元数据的 IM 提醒，模型明确辨认来源，通过；本轮首个 SessionStart 未携带邮件通知 |
| 批读与确认 | 三条有效消息一次批读；read 后未读仍为3；ack实际receipt后为0，通过 |
| 旧单替换 | supersedes保留关联，当前批读不含旧正文，通过 |
| 交付 | Qoder通过stdin JSON向测试manager信箱回传实质结论，通过 |
| 维护提醒 | 临时频率3次工具调用实际触发；不算默认50次验收 |
| 权限 | 普通权限模式，测试审批由主管逐项处理；不声称无人值守自动批准 |
| 当前生产适配/空闲唤醒 | Qoder尚未接入，未验；本轮不修改生产绑定或wake实现 |
| compact/resume | 本轮未复测；启动证据不能替代恢复验收 |

核对以原生hook记录、模型记录与信箱操作结果三者交叉为准，不能只相信模型“成功”的自述。本轮16项信箱测试、4项nodeterm唤醒测试通过。

必须区分 **核心信箱能力**、**测试适配器**、**生产集成**：`team.mjs` 交互命令当前从 Codex 环境推导 session；`wake.mjs` 识别 Codex 回合日志和输入提示。Qoder 的原生 hook 可用，不自动代表这两层也支持 Qoder。尚未接入时应明确人工/受控启动读信，不能伪称自动空闲唤醒。

复核命令：`node --no-warnings --test scripts/agent-mail/*.test.mjs`；`vitest run src/core/pty-mail-wake.test.ts`。单测不能代替真实 CLI 的启动、恢复、工具回调、草稿/审批/中断和空闲唤醒验收。

## 7. 发布与文档闭环

改机制同时改唯一协议、功能说明与安装指针；提交后同步本机副本。已有项目手工复制的指针不在全局安装器自动覆盖范围内，需逐一核对。长驻模型不会因为磁盘改了就自动看到新条款；只能通过下一次实际读取/恢复验证，不能把写盘称作全员已理解。

发布前按改动运行必要检查，检查 canonical 产物和远端 commit。只提交审阅过的文件，不顺带提交凭据、个人信箱/日志或未核实改动；保留未验边界，交付时说明代码已上传、安装同步和运行验收各自状态。
