# Nodeterm Agent IM 特性规格

状态：需求定义，待实现与验收。

## 1. 特性目标

为 nodeterm 中的 agent 提供统一、持久、可恢复的异步通信能力。消息正文存于信箱，通知只提示有未读消息；agent 按需批读、处理和确认。

该能力解决直接向终端提交消息正文带来的上下文干扰、迟到消息混淆、重复唤醒和待处理状态丢失问题。

核心原则：

- **统一底层**：不同 CLI 使用相同的通信身份、消息语义和操作接口。
- **存储与通知分离**：消息持久化不依赖收件人在线；提醒不自动注入正文。
- **可暂缓**：agent 可以不立即读信，未读状态持续保留。
- **安全唤醒**：不覆盖用户输入、不干扰审批、不擅自恢复用户中断的工作。
- **状态可核对**：存储、提醒、读取、确认和业务完成分别记录，不相互替代。

## 2. 适用范围

支持 nodeterm 管理的同类与混合 CLI 团队。首批完整验收覆盖纯 Qoder、纯 Codex 和 Qoder/Codex 混合团队。

统一能力随 nodeterm 部署，不依赖特定用户目录、预设成员名单或项目私有脚本。不同 CLI 的生命周期和输入控制差异由适配层处理；新增 CLI 不得复制一套独立 IM 实现。

本特性不包含跨机器消息同步、云端聊天服务、复杂聊天界面、群聊广播或完整业务任务管理系统。

## 3. 概念与职责

### 3.1 核心对象

| 对象 | 定义 |
|---|---|
| 通信成员 | 项目内稳定的收发身份；显示名称不是身份凭证 |
| 运行绑定 | 通信成员与当前 node、CLI session、运行实例之间经验证的关联 |
| 消息 | 包含ID、发送方、收件人、线程、正文、创建时间、重试键和可选替代关系的持久记录 |
| 线程 | 同一事项的消息集合；线程不扩大收件权限 |
| 读取批次 | 一次实际返回的消息快照及其确认凭据 receipt |
| 通知 | 未读数量、必要元数据及读信入口，不包含消息正文 |

### 3.2 系统职责

| 组件 | 职责 |
|---|---|
| IM公共层 | 消息存储、路由、批读、确认、历史、幂等、替代关系及通知调度 |
| 节点与身份层 | 成员登记、运行绑定、创建与恢复核验、项目通信边界 |
| CLI适配层 | 提供统一的运行状态证据、安全提醒边界及唤醒能力 |
| Agent | 使用统一接口收发，判断并处理消息，交付业务结果 |

具体数据库、目录结构及进程间通信方式不属于本规格的强制约束。

## 4. 功能要求

### IM-01：成员初始化与恢复

1. 通过受支持流程创建 agent 时，nodeterm 在验证真实运行身份后完成 IM 初始化，并提供统一操作入口。
2. 初始化状态须区分节点创建、启动投递、身份确认和IM就绪；终端存活不代表IM就绪。
3. 恢复已有 session 时复核绑定，保留原成员的消息与未读状态。
4. 改名不改变成员身份。新session、复制项目或替换节点不得仅凭名称继承旧绑定；无法证明归属时进入待接管状态。
5. Agent不得自行声明他人身份，或通过伪造其他CLI的环境变量获取收发能力。
6. 首任务由已有启动入口交付；初始化失败不得通过反复向终端塞正文补救。

### IM-02：消息存储与路由

1. 发送成功表示消息已持久存储，不表示已提醒、已读或已执行。
2. 收件人和项目边界明确。A发给B的消息不得进入C的信箱或上下文；线程名称相同不构成共享授权。
3. 同一发送方使用相同重试键和相同内容重复发送，仅保存一条；同键不同内容明确拒绝。
4. 支持替代自己向同一收件人、同一线程发送的有效消息。默认待处理视图排除被替代正文，历史保留替代链。
5. 替代消息不撤销已执行的动作，也不自动终止业务任务。
6. 消息来源明确标为同事通信，不自动提升为用户授权。

### IM-03：读取与确认

1. 支持查询未读元数据、按线程有界批读、显式确认和历史查询。合法单条消息不得因编码后超出通常批次预算而永久阻塞队首；应可完整返回，并推进确认与历史游标。
2. 读取返回receipt，不自动清除未读状态。
3. 确认只作用于该receipt实际包含的消息；批读期间新到或未返回的消息不得被确认。
4. 重复确认应幂等；无效、越权或旧绑定的receipt明确拒绝。
5. 读取、确认均不自动向发送方发一封回信，避免回执循环。
6. 确认表示该批消息已审阅，不代表业务接单、执行成功或任务完成。

### IM-04：通知与自动唤醒

1. 消息先存储，再按收件人状态调度通知。通知不包含正文。
2. 多封消息合并提醒；同一批未读不得导致持续重复开回合。
3. 未读状态与通知去重状态分离。旧消息未确认时，后来新消息仍具有独立的提醒资格。
4. 工作中在CLI支持的安全回调边界提醒，不强行打断推理或正在运行的工具；暂不可提醒时保持待提醒状态。
5. 正常空闲且确认可安全输入时，自动提交一次短读信提醒，启动收件人的读信回合。
6. 有草稿、审批、用户中断、未知运行状态或绑定异常时暂停主动唤醒；原因可查询。
7. 条件变化后重新评估。用户中断保持暂停，直到用户明确恢复或启动新回合，不因新信到达擅自解除。
8. 无法确定提醒是否已提交时标记投递不确定，不盲目无限重试。存储幂等不能解释为模型执行恰好一次。
9. 优先使用事件驱动，不依赖频繁扫描对话或固定间隔强制唤醒。

### IM-05：与编排衔接

1. 复用nodeterm现有节点创建、任务启动、session恢复和依赖编排机制。
2. 普通进度和结果正文通过IM交付；显式编排完成信号继续驱动依赖，不额外注入重复正文通知。
3. 回合结束、消息确认和业务完成保持独立；上一任务的成功结果不得释放新任务的下游依赖。
4. 使用IM的项目关闭旧正文推送路径，避免同一消息经两套通道重复进入上下文。
5. 创建节点不等于永久订阅其所有后续工作；汇报对象由当前任务的明确收件人决定。

### IM-06：持久性与运行恢复

1. 回合结束、上下文压缩、CLI退出和应用重启不得丢失消息、未读状态及历史。
2. 恢复通知调度前重新核对实际运行绑定，不仅依据画布保存状态。
3. 正常恢复后可继续读取未确认消息；不得自动重放已确认正文或重新执行历史任务。
4. 不无差别唤醒全部成员，不恢复已明确取消或中断的任务。
5. 存储容量、批次大小和历史清理策略须明确；达到限制时返回可诊断错误，不静默丢信。

### IM-07：CLI兼容与部署

1. 各CLI共享同一IM公共层和接口；适配层只处理运行身份、生命周期、安全边界与输入控制差异。
2. 优先复用nodeterm已有CLI集成，不要求团队为每种CLI或成员维护独立收发脚本。
3. 适配器明确声明支持的能力。无法安全自动唤醒的CLI必须显示限制，不能静默降级为盲目输入。
4. 新环境安装后，使用产品提供的配置和启动流程即可建立团队，不依赖开发机上的个人资产。
5. 功能支持声明以对应CLI的实际验收为准，不从一个CLI的成功推导所有CLI均支持。

### IM-08：可观测性与边界

1. 可核对消息ID、存储时间、运行绑定、通知尝试、暂缓原因及确认状态。
2. “提醒已提交”不得显示为“agent已读取或执行”。
3. 能定位重复提醒、漏唤醒、身份失配和恢复失败，不要求主管持续轮询其他agent。
4. 消息和历史由IM统一管理，诊断信息避免无必要地复制正文。
5. 成员绑定用于防误路由，不构成同一OS账户下恶意进程之间的安全沙箱。
6. 系统保证受支持范围内的存储与调度行为，不保证模型必然理解消息或正确完成业务任务。

## 5. 统一操作契约

以下为语义接口，命令名称与载体可沿用现有实现，但所有CLI必须一致。

| 操作 | 输入 | 输出与副作用 |
|---|---|---|
| send | 收件人、线程、正文、重试键、可选被替代消息ID | 持久消息ID及是否为重试；不承诺接收方已执行 |
| status / list | 可选查询范围 | 未读数量与元数据；不消费消息 |
| read | 可选线程、批次范围 | 消息快照及receipt；未读保持 |
| ack | receipt | 确认该快照；不确认后来新信，不产生回信 |
| history | 线程、游标 | 有权限的历史及替代关系；不重新激活旧消息 |

## 6. 状态模型与通知决策

状态模型使用彼此独立的维度，不把“消息未读”“agent空闲”“可以输入”合并成一个枚举。以下为目标状态定义，非现有代码完成声明。

### 6.1 持久状态与运行观测

| 维度 | 状态/字段 | 更新依据 |
|---|---|---|
| 消息确认 | 未确认 / 已确认；读取批次独立保存 | 持久入库、实际read快照、有效ack |
| 消息有效性 | 当前有效 / 已被替代 | 合法supersedes；与确认状态独立 |
| 成员绑定 | 待验证 / 有效 / 已失效；binding epoch | 真实session/node核验或显式接管；变更递增epoch |
| CLI生命周期 | 未运行 / 启动中 / 工作中 / 正常空闲 / 未知 | 适配器原生证据，带运行代次、事件序号及有效期 |
| 主动唤醒保护 | 草稿、审批、用户暂停、能力不足、证据过期 | 独立保护标记，可同时存在；全部解除才可主动唤醒 |
| 通知尝试 | 待评估 / 暂缓 / 已占用 / 已提交 / 确认未提交 / 结果不确定 | 调度器持久记录attempt、收件人、binding epoch和消息水位 |

“已读”不是一个会自动清除未读的消息状态：read创建批次，ack才确认。已提交提醒也不改变消息确认状态。

### 6.2 调度规则

| 条件/事件 | 行为 |
|---|---|
| 新信持久入库 | 更新有效未读水位，触发评估；不立即假定可输入 |
| 工作中到达安全hook边界 | 合并元数据提醒；按实际回合去重，不经终端插入正文 |
| 正常空闲、绑定有效、无保护标记 | 原子占用一次通知尝试，提交前再次验证，再提交短提醒 |
| 草稿、审批、暂停、过期证据、未知或失效身份 | 暂缓并记录所有原因，不消费待提醒资格 |
| 保护条件变化或有效生命周期事件 | 重新评估待提醒；不得由“新信到达”解除用户暂停 |
| 提醒提交明确失败且无输入发生 | 释放尝试，保留待提醒；受控退避重试，不持续忙循环 |
| 提醒提交成功 | 记录对应消息水位；不确认消息、不认定模型已经读信 |
| 提交后进程崩溃或结果无法确认 | 标记不确定；先核对可用投递证据，不直接重发 |
| ack / supersedes | 重新计算有效未读；未发送的过时提醒取消或合并 |
| 应用恢复 / 绑定变化 | 旧运行证据失效；旧epoch尝试不得发给新绑定；重建核验后再调度 |

### 6.3 必须保持的不变量

- 同一成员同一binding epoch最多有一个正在提交的主动通知尝试；并发入库不能重复触发多个回合。
- 被动hook提醒水位与主动wake水位分别记录；旧hook记录不能吞掉随后新信的空闲唤醒。
- 已提醒但未确认的旧信持续显示未读，不反复自动开回合。新信、明确恢复等有效事件按规则重新评估。
- 提交期间到达的新信不得被旧尝试误记为已提醒；尝试只覆盖其实际通知快照。
- 空闲证据不能跨运行代次、跨session或无限期复用；乱序旧事件不得覆盖新的忙碌/中断状态。
- 草稿检查与实际写入存在竞争窗口。输入传输层必须提供协调/排他或等价安全保证；只有两次截图或两次空框检查不足以证明原子安全，能力不足时不得宣称支持无干扰自动唤醒。
- 无法保证外部CLI提交恰好一次时，保留“不确定”而不伪造成功或盲目重试。
- 邮件状态不驱动业务完成。编排释放仍核对当前任务对应的有效结果。

实现前需要明确每个CLI对上述状态的真实证据来源，以及提交协调能力；不允许用固定时间等待替代身份、空闲或输入安全证明。

## 7. 验收标准

| 场景 | 通过条件 |
|---|---|
| 干净环境纯Qoder团队 | 通过正常流程创建主管与两个成员，自动完成IM初始化；无需项目私有脚本即可完成派单、收信和交付 |
| 纯Codex及混合团队 | 使用相同接口完成往返；混合CLI不要求独立信箱实现 |
| 批读与并发来信 | read后未读保持；ack只确认原批次，新到消息仍未读 |
| 重试与旧单替代 | 重复发送不重复存储；冲突重试拒绝；旧单不冒充当前任务，历史可追溯 |
| 空闲与工作中收信 | 空闲自动唤醒；工作中安全边界提示；多封信合并且不强塞正文 |
| 草稿、审批、中断 | 不覆盖输入、不替人审批、不擅自恢复；暂缓原因可查 |
| 身份与项目隔离 | 消息不串台；同名、旧session或复制项目不能错误继承身份 |
| 重启、resume、compact | 消息和未读保留，正确恢复绑定与通知，不重放已确认正文 |
| 完整编排链 | 创建→派单→结果→下游依赖均对应当前任务，无旧成功误释放或双通道重复通知 |
| 异常与恢复 | 存储失败、CLI退出、绑定变化、投递不确定均有明确结果，不静默丢信或无限重试 |

验收须记录CLI及版本、前置状态、实际步骤、预期、结果与证据。单元测试覆盖状态和存储规则，真实CLI测试覆盖创建、身份、提醒、输入保护及恢复；二者不能互相替代。未通过的能力明确标为未支持或待验。
